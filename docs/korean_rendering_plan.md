# Wizardry 7 Gold 인게임 한글 출력 조사

## 결론

원본 `VBFONT*.VGA`를 단순 교체하는 것만으로는 전체 한국어를 표시할 수 없다. 글꼴 로더와 출력기가 1바이트/128글자 구조를 전제로 만들어져 있기 때문이다.

가장 현실적인 1차 구현은 `winmm.dll` 프록시로 문자 출력 함수를 후킹하고, 2바이트 한글 코드를 받으면 API 글꼴의 해당 글리프를 원본 글꼴의 예약 슬롯에 동적으로 복사한 뒤 기존 출력 함수를 호출하는 방식이다. 이렇게 하면 원본의 팔레트, 클리핑, 화면 버퍼 출력 코드를 그대로 이용할 수 있다.

## 프로토타입 검증 결과 (2026-08-22)

이 방식으로 실제 GOG Gold 실행 파일에서 한글 출력에 성공했다.

- x86 `winmm.dll` 프록시를 게임 폴더에 배치해 정상 부팅 확인
- `0x00425D90` 후크 설치와 시스템 WinMM 8개 함수 전달 확인
- `Galmuri7 8x8`의 KS X 1001 글리프 2,350개 로드 확인
- 전용 2바이트 코드 `97 A2`를 글리프 인덱스 2,210의 `한`으로 디코딩
- 원본 6x6 글꼴에서는 판독성이 낮아 `VBFONT0.VGA`를 8x8 컨테이너로 확장
- 메인 메뉴의 `CREATE` 자리를 바꾼 스모크 테스트에서 8x8 `한` 출력 확인
- 실행 로그에서 `Rendered Hangul glyph: index=2210 font=0` 확인
- `0x00426CC7` 문자열 폭 계산 함수를 추가 후킹하고 같은 빌드의 정상 부팅 확인

현재 프로토타입은 **문자 그림 출력과 기본 문자열 폭 계산**까지 구현한 상태다. 긴 한국어 문장을 안정적으로 표시하려면 줄바꿈과 메시지 제어코드 경로도 2바이트 한글을 한 글자로 취급하는지 추가 검증해야 한다.

## 확인한 VBFONT 구조

`VBFONT2.VGA` 기준:

- 최대 폭: 12px (`+0x00`)
- 높이: 14px (`+0x01`)
- 한 행 바이트 수: 2 (`+0x03`)
- 글리프 수: 128 (`+0x05`)
- 첫 번째 비트맵의 글리프당 크기: 28바이트 (`+0x0A`)
- 두 번째 비트맵의 글리프당 크기: 28바이트 (`+0x0E`)
- 문자/폭 표: `+0x10`, 문자마다 2바이트
- 비트맵 시작: `+0x110`
- 첫 번째 비트 평면: 128 × 28바이트
- 두 번째 비트 평면: 128 × 28바이트
- 총 파일 크기: 7,440바이트

`tools/analyze_vbfont.mjs`로 `VBFONT0`, `VBFONT2`, `VBFONT3`의 글리프를 실제 이미지로 복원해 구조를 검증했다.

## 실행 파일에서 확인한 제한

GOG Gold의 `WIZARD.EXE`는 1996년 x86 PE32이며 이미지 베이스는 `0x00400000`이다.

- `0x00426351`: 글꼴 로더
- `0x004263D8`: 헤더와 문자/폭 표를 고정 크기 `0x110`바이트로 할당
- `0x0042641C`: 파일에서 `0x110`바이트만 먼저 읽음
- `0x0042644B` 이후: 헤더의 글리프 수 × 글리프 크기만큼 비트맵을 별도 할당
- `0x00425D90`: 한 글자 비트맵 출력
- `0x00425DE1` 이후: 입력 바이트를 글리프 수로 나눈 나머지를 글리프 번호로 사용
- `0x00426124` 이후: 글리프 번호로 문자 폭 표를 조회하고 커서를 전진
- `0x00426567`: NUL 종료 문자열을 한 바이트씩 순회하는 출력 루프

따라서 글리프 수를 늘리는 파일 수정만으로는 표 크기와 1바이트 문자 순회를 넘을 수 없다.

## 권장 구현

### 1. 2바이트 한글 인코딩

번역 삽입 도구가 한국어 글자를 전용 2바이트 코드로 변환한다. 첫 바이트는 한글 시작 범위, 두 번째 바이트는 글리프 번호의 나머지로 사용한다. ASCII와 게임 제어코드는 기존 값 그대로 둔다.

API의 KS X 1001 글꼴은 2,350자를 제공하므로 현재 번역에는 우선 이 글리프 맵을 사용한다. 번역 검증 단계에서 지원되지 않는 음절을 자동 검출한다.

### 2. `winmm.dll` 프록시 후크

게임이 이미 `WINMM.dll`을 불러오므로, 게임 폴더의 x86 프록시 DLL이 시스템 `winmm.dll`의 다음 함수를 전달하면서 초기화 때 출력 함수를 후킹한다.

- `timeGetSystemTime`
- `mciSendStringA`
- `timeEndPeriod`
- `timeBeginPeriod`
- `timeGetTime`
- `sndPlaySoundA`
- `mciSendCommandA`
- `mciGetErrorStringA`
- `PlaySoundW` (`Launch.exe`가 요구하므로 런처 호환용으로 전달)

원본 실행 파일은 ASLR 플래그가 없으므로 조사한 주소를 그대로 사용할 수 있지만, 안전을 위해 코드 바이트 서명을 먼저 확인한 뒤 후킹한다.

GOG의 `Launch.exe`도 게임 폴더의 `winmm.dll`을 먼저 불러온다. 따라서 프록시는 런처에서 `PlaySoundW`를 시스템 WinMM으로 전달하되, 고정 주소 후크는 `WIZARD.EXE` 또는 `WIZARD_900.EXE` 프로세스에서만 설치한다.

### 3. 동적 예약 슬롯

2바이트 코드가 완성되면 활성 글꼴의 비트맵 버퍼에서 사용하지 않는 한 슬롯에 한국어 비트맵을 복사한다. 이어서 원본 `0x00425D90`을 해당 슬롯 번호로 호출한다. 이 방식은 직접 화면 버퍼를 조작하는 것보다 원본 색상과 클리핑 동작을 보존하기 쉽다.

문자열 길이 계산, 줄바꿈, 가운데 정렬에서 2바이트 글자를 한 글자로 세도록 폭 계산 루틴도 함께 후킹해야 한다.

## 폰트 선택

- 작은 글꼴은 API에서 받은 네이티브 `Galmuri7 8×8`을 사용한다.
- `Galmuri9 10×10`을 8×8로 자르면 획이 클리핑되고, 7×7로 축소하면 주요 획이 소실되어 판독성이 떨어지는 것을 인게임에서 확인했다.
- 작은 글꼴(`font_index == 0`)의 한글만 원본 출력 좌표보다 1픽셀 위에 그린다. 글리프 크기는 바꾸지 않으며 영문과 다른 글꼴의 기준선에는 영향을 주지 않는다.
- 본문용 큰 글꼴은 12×14로 변환한 Galmuri 계열 또는 DOSGothic을 계속 검토한다.
- API에서 받은 `Galmuri7 8×8`과 `DOSGothic 16×16`의 `.bin`, 글리프 맵, TTF를 원본으로 사용한다.
- 실제 Wizardry 7용 12×14/8×8 산출물이 확정되면 `/api/font_upload`로 다시 업로드
